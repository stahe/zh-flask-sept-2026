    12. 结论

    本文档介绍了使用 [Flask] 框架开发 MVC Web 应用程序的过程：该应用程序的 HTML 页面由服务器使用 [Jinja2] 视图生成，不使用浏览器端的 [JavaScript] 框架。本文档分步遵循 [Spring MVC] 课程，而该课程本身又建立在 [ASP.NET Core MVC] 和 [NestJS] 课程的基础之上：从操作和路由到视图、表单、国际化、安全和数据访问，最后是一个完整的案例研究。

    与 [Spring MVC] 相比，需要注意的要点有：

    • [Flask] 是一个微框架：它提供路由、请求和响应、[Jinja2] 视图以及会话管理，仅此而已。其他一切（验证、表单、安全、数据访问、翻译）都由开发者选择的库来处理，或由开发者自己编写。这意味着要编写更多的代码，但这些代码是透明的：没有任何事情是“靠魔法”发生的，你可以追踪每个对象，从它的创建（在 [create_app] 中）到它的使用；
    • 没有依赖注入容器：共享对象由工厂创建，存放在 [app.extensions] 中，并通过 [current_app] 获取。对于这种规模的应用程序，这简单而且够用；
    • 对象 [request]、[g]、[session] 和 [current_app] 是代理 ，在请求期间指向该请求的对象。它们省去了在函数之间传递请求的麻烦，但只能在处理请求期间（或在手动创建的应用程序上下文中）使用；
    • [Python] 的装饰器 与 [Java] 的注解作用相同：路由、标记（[@public]）和访问控制（[@roles_required]）。但装饰器只是一个函数，你自己只需几行就能写出来；
    • [Python] 是一种动态类型语言：类型注解（[list[Doctor]]、[Protocol]、泛型类）为代码提供文档并指导编辑器，但不会在运行时检查。[Pylance] （在 [Visual Studio Code] 中）或 [mypy] 之类的工具会在执行前检查它们；
    • [SQLAlchemy] 需要编写 DAO 层（每个请求几行代码），但它的查询是用 [Python] 对象构造的，仍然贴近它所生成的 SQL，而显示 SQL（[SQL_ECHO]）命令可以让你验证发送给数据库的是什么。关系的加载是显式控制的，逐个查询地控制；
    • [Jinja2] 视图把 HTML 与 [{{ }}] / [{% %}] 标签混合在一起：它们不像 [Thymeleaf] 的视图那样是有效的 HTML 页面，但它们的语言类似于 [Python]，功能强大（过滤器、宏、模板继承），并且自动转义可防止 HTML 注入。

    案例研究表明，不依赖 [JavaScript] 的经典 HTML 应用程序，仍然是一种简单而稳健的解决方案：每个页面都是一个 URL，浏览器的“后退”按钮可以正常工作，服务器掌控一切。对 [JavaScript] 的有限使用（确认窗口）改善了用户体验，而应用程序的运行并不依赖它。

    如需了解更多信息，可以查阅 [Flask] （flask.palletsprojects.com）、[Jinja2] （jinja.palletsprojects.com）、[Werkzeug]（werkzeug.palletsprojects.com）、[WTForms] （wtforms.readthedocs.io）和 [Flask-WTF]（flask-wtf.readthedocs.io）、[SQLAlchemy] （docs.sqlalchemy.org）、[Pydantic]（docs.pydantic.dev）的文档，并将本应用程序与其对应版本 [Spring MVC]、[ASP.NET Core MVC]、和 [NestJS] 进行比较。
